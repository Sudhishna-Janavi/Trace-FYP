## The datasets

### US — the dataset the model is trained on

`dataset/US/transactions-synthetic.csv` — 68,000 rows, two columns
(`description`, `category`), 17 categories, 4,000 rows each.

Source: <https://huggingface.co/datasets/DoDataThings/us-bank-transaction-categories-v2>
Licence: MIT.

**It is synthetic, and that must be stated plainly in the report.** The
descriptions are generated by an open-source generator, not taken from real bank
statements. What makes it defensible is that it is third-party (not written by
this project), publicly downloadable, reproducible because the generator is
open source, and modelled on eight real US bank statement layouts with over 500
real merchant names.

No public dataset of *real* labelled bank-transaction descriptions exists,
because a transaction narrative names real people and places and is therefore
personal data. Published work either uses proprietary in-house data
([BTG Pactual, 2023](https://arxiv.org/pdf/2312.07730)), develops weak
supervision specifically to avoid needing labels
([Toran et al., 2023](https://arxiv.org/abs/2305.18430)), or releases a real
corpus only on request ([García-Méndez et al., 2024](https://arxiv.org/abs/2404.08664)).

### Indian — held in reserve

`dataset/Indian/` — 11,000 rows, 5 categories. Downloaded, **not yet used.**
Source: <https://www.kaggle.com/datasets/coderanand/indian-banking-transaction-text-dataset>

Intended later as an independent second source, to show the method is not an
artefact of one dataset.

Two things to know before using it. Its amounts are meaningless: every category
has a median near ₹25,000 drawn uniformly from ₹0–50,000, so a food delivery can
cost ₹37,000. And the amount is written *inside* the description
(`Swiggy order payment | Ref:0f8f77bb | Amount: INR 37090.45`), so that suffix
must be stripped before use, leaving `Swiggy order payment`.

## Unit 1 — data preparation

Run with:

```
python scripts/prepare_dataset.py \
    --input dataset/US/transactions-synthetic.csv \
    --outdir dataset/processed
```

It does four things.

### 1. One shared normalisation

Every model receives exactly the same text, so the comparison measures models
rather than preprocessing choices.

| Before | After |
|---|---|
| `[debit] PUBLIX 7860 UNIVERSITY LN OAKLAND 94601-4574CA USA` | `DEBIT PUBLIX <NUM> UNIVERSITY LN OAKLAND <NUM> 4574CA USA` |
| `[credit] US GOVERNMENT DIR DEP PPD ID: 547185326` | `CREDIT US GOVERNMENT DIR DEP PPD ID <NUM>` |
| `[debit] PYPL*365 MARKET` | `DEBIT PYPL 365 MARKET` |

The rules: uppercase; `[debit]`/`[credit]` becomes a leading `DEBIT`/`CREDIT`
token; runs of four or more digits become `<NUM>`; punctuation becomes a space;
repeated whitespace collapses.

Two choices worth explaining. The direction marker is **kept** because the
dataset's documentation names it as the primary signal separating `Income` from
`Transfer` — `[credit] VENMO CASHOUT` is income, `[debit] VENMO PAYMENT TO` is a
transfer. Using it is realistic rather than generous, since a real system always
knows the direction from the sign of the amount. And only long digit runs are
replaced, so store and reference numbers stop being memorised while `365 Market`
keeps its 365.

### 2. Deduplication, before splitting

The raw file repeats itself heavily: `DEBIT MORTGAGE PAYMENT` appears 607 times.
Deduplicating on (normalised text, category) reduces 68,000 rows to **31,863**.

This happens **before** the split. Doing it afterwards would be pointless,
because the duplicates would already have crossed the train/test boundary and
the test set would be measuring recall of memorised strings.

Ten descriptions carry two different categories. These are genuine ambiguity —
`DEBIT BATH BODY WORKS <NUM>` is labelled both `Shopping` and `Personal Care` —
and are deliberately kept, so a model is free to be uncertain there.

### 3. Two evaluation protocols

Both are 70/15/15 over the same deduplicated rows. They answer different
questions and are both reported.

**Split A, stratified random.** Rows are shuffled, keeping each category's
proportion. A merchant can appear on both sides. This models a returning user:
a new transaction from a shop the system already knows.

**Split B, merchant-grouped.** Every row of a merchant lands in one partition
only. This models a new user whose shops the system has never encountered.

Worked example. Suppose Starbucks appears six times, spelled differently each
time:

```
① DEBIT STARBUCKS CHICAGO        ④ DEBIT CLV STARBUCKS PHILADELPHIA
② DEBIT PAYPAL STARBUCKS         ⑤ DEBIT STARBUCKS MARKET CT MIAMI
③ DEBIT TST STARBUCKS            ⑥ DEBIT PYPL STARBUCKS
```

Split A might train on ① ② ③ ④ and test on ⑤ ⑥. The model has already learned
that `STARBUCKS` means Restaurants, so it only has to recognise the word.

Split B puts all six on one side. If they are in test, the model has never seen
the word `STARBUCKS` and must reason from other evidence — that `TST*` is a
Toast till, which restaurants use. That is much harder, and much closer to what
happens when a real new user signs up.

### 4. Identifying merchants

Grouping by merchant is the only difficult part of Unit 1, and naive approaches
fail quietly.

Taking the first word fails because one brand produces many first words across
statement formats (`AMAZON`, `AMZN`, `AMAZON MKTPL`), and because descriptions
often lead with a generic word belonging to hundreds of merchants
(`STARBUCKS <NUM> MARKET CT` would be keyed `MARKET`).

Instead, each token is scored by its *spread*: how many distinct leading words
it co-occurs with. `MARKET` spreads across hundreds of merchants; `STARBUCKS`
across about two. Each row is keyed by its **narrowest-spread token**, which is
the word that most specifically identifies the merchant. This finds 1,454
merchants, the largest being `ZELLE` with 641 rows.

## Known limitations

Three, all measured rather than assumed.

**Deduplication unbalances the classes.** The raw file has exactly 4,000 rows
per category. Repetitive categories lose more rows to deduplication, so after it
`Restaurants` has 3,110 and `Rent` has 874 — a 3.6× spread. This is mild and is
handled by reporting **macro-F1**, which weights every category equally, and by
using class weights when fitting. Accuracy alone would favour the larger
categories and should not be the headline number.

**Split B still leaks a little.** No merchant group spans train and test, and
this is asserted in the script. But brands co-occur inside single descriptions —
`AMAZON PRIME` is keyed `PRIME` while `AMAZON MKTPL` is keyed `AMAZON` — so the
*word* `AMAZON` can still appear on both sides. Four probe brands do this:
`AMAZON`, `NETFLIX`, `UBER`, `COSTCO`.

A perfectly disjoint split is not constructible on this corpus: merging every
co-occurring brand pair transitively collapses most of the data into one group
that cannot then be split 70/15/15. The honest response is to measure it rather
than hide it. **46.3% of Split B's test rows (2,213) contain no merchant word
seen anywhere in training** — that subset is the true cold-start case and should
be reported as its own stratum alongside the overall figure.

**One identical text spans stratified train and test.** It is
`DEBIT BATH BODY WORKS <NUM>`, which carries two different categories, so both
copies survive deduplication and can fall on opposite sides. This is the
ambiguity case described above, not a defect.

## Unit 2 — model comparison

Six models, same input (`normalised_description`), same output (one of the 17
categories), same metrics. Compared on the **validation** sets; only the winner
is ever scored on test.

| # | Model | Machine learning? | State |
|---|---|---|---|
| 1 | Rule baseline | no | **done** |
| 1b | Merchant memory | no | **done** |
| 2 | Naive Bayes | yes | **done** |
| 3 | Logistic regression | yes | **done** |
| 4 | Linear SVM | yes | **done** |
| 5 | MiniLM embeddings | pre-trained encoder + learned head | **done** |

Run any model with `python scripts/run_model1_rules.py`; results are written to
`results/`.

### Model 1 — rule baseline

Hand-written patterns in `models/rule_baseline.py`. No learning takes place.
This is the control group: it establishes what plain keyword matching achieves,
and therefore what a learned model has to beat to be worth its complexity.

The patterns deliberately use **generic banking vocabulary only** — `MORTGAGE`,
`RENT`, `PAYROLL`, `OVERDRAFT FEE` — and never merchant brand names. A rule
saying "NETFLIX means Subscription" would score well on merchants already seen
while teaching us nothing about new ones, and would quietly turn the baseline
into a lookup table.

| Protocol | n | Accuracy | Macro-F1 | Coverage | Precision when it answered |
|---|---|---|---|---|---|
| Stratified (validation) | 4,780 | 0.1701 | 0.2924 | 17.3% | **98.2%** |
| Merchant held out (validation) | 4,780 | 0.1498 | 0.2196 | 15.0% | **100.0%** |
| of which strictly novel | 2,259 | 0.1253 | 0.1596 | 12.5% | **100.0%** |

**How to read this.** The accuracy and macro-F1 columns look poor, and they
should: the rules abstain on more than 80% of transactions, and every abstention
counts as a miss. The meaningful column is the last one. On the rows it does
answer, the rule layer is right 98 to 100% of the time.

**Precision does not fall as the task gets harder** — it is 98.2% on familiar
merchants and 100% on merchants never seen before. That is the whole argument
for keeping a rule layer in the final system: because the patterns describe
banking vocabulary rather than specific shops, they are unaffected by whether
the merchant is known, which is exactly where the learned models will turn out
to be weakest.

Four faults were found and fixed, all diagnosed on **train** rather than
validation, so the comparison set stays clean:

| Fault | Evidence on train | Fix |
|---|---|---|
| `Transfer` claimed incoming Zelle | `CREDIT ZELLE PAYMENT FROM MARGARET ROBINSON` is Income, 343 times | money arriving *from* a named person is income |
| `Insurance` matched software tiers | `TELEGRAM PREMIUM`, `ZOHO PREMIUM`, 76 times | bare `PREMIUM` removed |
| `Transportation` claimed airport parking | `AIRPORT PARKING INC` is Travel, 30 times | `PARKING` guarded against `AIRPORT` |
| `Subscription` was unresolvable | the word appears in `TICKETMASTER SUBSCRIPTION` (Entertainment), `SUBSCRIPTION PAYMENT DELL` (Shopping), `SUBSCRIPTION PAYMENT BRILLIANT ORG` (Education) | rule removed entirely |

The last one is a finding rather than a repair. Deciding `Subscription` requires
knowing the merchant, which is precisely what a rule layer cannot do and a
learned model can. The rule abstains instead of guessing, which is why coverage
fell from 19.6% to 17.3% while precision rose from 85.1% to 98.2%.

### Model 1b — Merchant memory

A lookup table, and the deliberate opposite of Model 1. The rule baseline
contains **no** merchant names; this one contains **nothing but** merchant names.
It records which category each merchant received during training and returns it
again later, abstaining when the merchant is unknown. Between them the two
bracket the problem, and the gap is the space the learned models must occupy.

The fingerprint is computed from a single description in isolation rather than
from the stored `merchant_key`, because that key was derived using statistics
over the whole corpus — information a deployed system would not have when one
new transaction arrives. Matching is exact; a fuzzy matcher would raise coverage,
so these figures are a lower bound.

| Protocol | n | Accuracy | Macro-F1 | Coverage | Precision when it answered |
|---|---|---|---|---|---|
| Stratified (validation) | 4,780 | 0.8140 | 0.8500 | **82.2%** | **99.1%** |
| Merchant held out (validation) | 4,812 | 0.0374 | 0.0752 | **3.8%** | 98.4% |
| of which strictly novel | 2,457 | 0.0016 | 0.0156 | **0.3%** | 57.1%* |

\* fired on roughly seven rows, so that precision is noise.

6,156 merchants were memorised from 22,297 training rows. The collapse from
82.2% coverage to 0.3% is not a failure of the method but its definition: a
lookup table cannot answer a question it has never been asked.

**The contrast with the rules is the point:**

| Layer | Stratified | Merchant held out | Strictly novel |
|---|---|---|---|
| Rules — merchant-**independent** | 17.3% | 16.8% | 15.8% |
| Merchant memory — merchant-**dependent** | 82.2% | 3.8% | 0.3% |

The rules barely move because they describe banking vocabulary. The memory
collapses because it describes nothing else. Neither is better; they fail in
different places, which is the argument for a cascade rather than a choice.

**How the work divides on the stratified protocol:**

| | Rows | Share |
|---|---|---|
| A rule answers, memory does not | 33 | 0.7% |
| Memory answers, no rule does | 3,133 | 65.5% |
| Both answer | 795 | 16.6% |
| **Neither answers — must go to a model** | **819** | **17.1%** |

Together the deterministic layers answer **82.9% of transactions at 99.3%
precision**, leaving 17.1% carrying neither recognisable vocabulary nor a known
merchant. That remainder is the genuine machine-learning problem.

**But that figure holds only for a returning user.** With merchants held out the
memory covers 3.8%, so the cascade falls to roughly 20% and the model carries
everything else. This is precisely why performance on unfamiliar merchants
decides which model to deploy.

### Model 2 — TF-IDF with multinomial Naive Bayes

The first model that learns. It counts how strongly each feature associates with
each category and applies Bayes' rule, assuming features are independent given
the category — an assumption text plainly violates, which is why it is called
naive. It is the **cheap learned baseline**: it trains in
0.58 seconds over 23,864 features, so anything
more expensive has to justify itself.

Models 2, 3 and 4 share the same TF-IDF representation (word 1–2 grams plus
character 3–4 grams, fitted on train only), so differences between them reflect
the classifier rather than the features.

| Protocol | n | Accuracy | Macro-F1 |
|---|---|---|---|
| Stratified (validation) | 4,780 | 0.9782 | **0.9809** |
| Merchant held out (validation) | 4,812 | 0.5939 | **0.5903** |
| of which strictly novel | 2,457 | 0.4461 | **0.4657** |

The model and the metric are identical across all three rows. The only thing
that changes is whether the merchant has been seen before, and macro-F1 falls by
0.515 between the easiest and hardest condition.
Merchant familiarity, not model quality, dominates the headline number.

**Where it holds up and where it fails.** Categories carrying their own
vocabulary survive the merchant holdout: Mortgage 0.954, Rent 0.930, Fees 0.888,
Utilities 0.818. Categories defined by *who the merchant is* collapse:
Education 0.230, Shopping 0.250, Income 0.345, Transportation 0.395.

**The largest single confusion is Income predicted as Transfer, 74.9% of Income
rows.** Both describe money moving, and without a recognisable payer the text
alone rarely separates them. This is worth noting because the rule baseline
classified Income at 100% precision using the direction marker and a short list
of payroll terms. Neither layer is better than the other; they fail in different
places, which is the argument for combining them.

Insurance also behaves as a sink: when the model is unsure it tends to answer
Insurance, absorbing 33% of Education, 21% of Entertainment and 18% of Travel.

## Correction made during Model 2

The first merchant split was defective and the error is recorded here rather
than quietly fixed.

Merchants were packed into partitions by **size alone**, ignoring category.
Categories differ in merchant shape: Rent is a handful of large landlords, while
Restaurants is thousands of small independents. Size-only packing therefore sent
every Rent merchant to training, leaving `Rent` with **0 validation and 0 test
rows**, and `Personal Care` with 1 and 6.

Those empty categories scored F1 = 0, not because the model failed but because
there was nothing to score, and that zero was then averaged into macro-F1. The
merchant-protocol figures were consequently wrong — reported as 0.5274 when the
corrected value is 0.5903.

The fix packs merchants **within each category**, so every category reaches all
three partitions while a merchant still belongs wholly to one. The smallest
category now has 126 validation rows instead of 0, and the script asserts this,
so the failure cannot recur silently.

### Model 3 — TF-IDF with logistic regression

Same features as Model 2, so the comparison isolates the classifier. Two
properties make this model matter to the project beyond its accuracy: it is
**linear**, so a feature's contribution is its weight times its value and the
explanation needs no approximation; and its probabilities are **fitted by
maximum likelihood**, so its confidence can be measured and trusted. The
architecture routes low-confidence predictions to human review, which only works
if the confidence means something.

| Protocol | n | Accuracy | Macro-F1 | ECE |
|---|---|---|---|---|
| Stratified (validation) | 4,780 | 0.9973 | **0.9976** | 0.0582 |
| Merchant held out (validation) | 4,812 | 0.6022 | **0.5980** | 0.0406 |
| of which strictly novel | 2,457 | 0.4550 | **0.4636** | 0.0509 |

**Accuracy is not the reason to prefer it.** Against Naive Bayes it gains
+0.0167 macro-F1 on the stratified protocol and +0.0077 with merchants held out,
but is **0.0021 worse** on the strictly novel subset — for roughly seven times
the training cost (3.97s against 0.58s).
If the comparison were accuracy alone, Naive Bayes would be the sensible choice.
The case for logistic regression rests on calibration and on exact
explainability, both of which the architecture depends on.

**Calibration is good across all three protocols** (ECE 0.04–0.06). It is mildly
*under*-confident where the task is easy (stating 0.939
while achieving 0.997) and mildly *over*-confident
on strictly novel merchants (0.496 stated
against 0.455 achieved). Erring toward caution on
easy cases and only slightly overreaching on hard ones is the behaviour a review
gate wants.

**The weights explain the whole experiment.** Reading what the model learned
shows directly why each category survives or fails when merchants are held out:

| Category | Strongest evidence learned | Merchant-held-out F1 |
|---|---|---|
| Mortgage | `mortgage` `cu` `mtg` `escrow` — generic banking vocabulary | **0.961** |
| Shopping | `amazon com` `tiktok shop` `mercari` `target` `offerup` — brand names | **0.303** |

Categories whose evidence is vocabulary transfer to unseen merchants; categories
whose evidence is a list of shops cannot. This is visible in the fitted weights
before any evaluation is run, and it is the clearest single illustration of the
project's central finding.

The dominant error is unchanged from Model 2: **73.7% of Income is predicted as
Transfer** once merchants are unfamiliar, against the rule baseline's 100%
precision on Income.

### Model 4 — TF-IDF with a calibrated linear SVM

A linear SVM finds the widest-margin boundary between classes and is usually the
strongest classical linear model on sparse text. It has one complication: **it
produces distances, not probabilities.** A distance of 2.0 does not mean twice as
likely, so the raw output is unusable as a confidence score. `CalibratedClassifierCV`
wraps it and learns the distance-to-probability mapping by fitting a sigmoid on
held-out training folds (Platt scaling) — a second model fitted on top of the first.

| Protocol | n | Accuracy | Macro-F1 | ECE |
|---|---|---|---|---|
| Stratified (validation) | 4,780 | 0.9981 | **0.9984** | 0.0068 |
| Merchant held out (validation) | 4,812 | 0.6170 | **0.6393** | 0.1452 |
| of which strictly novel | 2,457 | 0.4481 | **0.5146** | 0.2372 |

**The SVM is the most accurate model so far on every protocol**, and the margin
widens as the task gets harder: +0.041 macro-F1 over logistic regression with
merchants held out, and **+0.051 on strictly novel merchants**, where accuracy is
scarcest and therefore most valuable.

**But its confidence degrades badly under distribution shift**, and this is the
more interesting result:

| Protocol | Logistic regression ECE | SVM ECE |
|---|---|---|
| Stratified | 0.0582 | **0.0068** — better |
| Merchant held out | **0.0406** | 0.1452 — 3.6× worse |
| Strictly novel | **0.0509** | 0.2372 — 4.7× worse |

The pattern is explicable. Platt scaling is fitted on held-out folds *of the
training data*, which resemble the stratified validation set and do not resemble
a set of merchants the model has never seen. **Post-hoc calibration generalises
poorly under distribution shift**, so the wrapper works where it is least needed
and fails where it matters most.

Concretely, on strictly novel merchants the SVM states
0.685 confidence and achieves
0.448 accuracy — an overconfidence of
+0.237. A review gate reading that score would
wave through wrong answers precisely in the situation it exists to catch.

This sets up the deployment decision: the most accurate model is not
automatically the right one when the architecture depends on the confidence score
meaning something.

### Model 5 — MiniLM sentence embeddings with a logistic-regression head

The only model that represents *meaning* rather than counting surface patterns.
`all-MiniLM-L6-v2` is a small transformer, pre-trained by others, that maps text
to 384 numbers positioned so similar meanings land near one
another. **The encoder is downloaded and frozen** — no neural network is trained
here. Only a logistic-regression head is fitted, identical to Model 3, so the
comparison between Models 3 and 5 isolates the representation.

| Protocol | n | Accuracy | Macro-F1 | ECE |
|---|---|---|---|---|
| Stratified (validation) | 4,780 | 0.9029 | **0.9167** | 0.1096 |
| Merchant held out (validation) | 4,812 | 0.6311 | **0.6479** | 0.0360 |
| of which strictly novel | 2,457 | 0.5710 | **0.5936** | 0.0436 |

**The result reverses depending on the protocol, and that is the finding.**
MiniLM is the *weakest* of the learned models where merchants recur (0.9167
against 0.9984 for the SVM) and the *strongest* where they do not — 0.6479 with
merchants held out, and **0.5936 on strictly novel merchants against the SVM's
0.5146**, a margin of +0.079.

The reason is what each representation can exploit. TF-IDF wins on familiar
merchants because a brand name is a perfectly discriminative token: having seen
`SAFEWAY` labelled Groceries, recognising it again is trivial and no semantic
understanding is needed. That advantage vanishes the instant the merchant is
new, because the token is not in the vocabulary. A sentence encoder has no such
cliff — it still places an unfamiliar merchant somewhere sensible using word
fragments, format cues and the shape of the name.

**This matters for deployment.** A finance application meets unfamiliar merchants
constantly: every new user arrives with shops the system has never seen. The
protocol that matters most in practice is the one MiniLM leads.

**Settling the deferred normalisation question.** Unit 1 left open whether the
shared uppercase-with-`<NUM>` text handicaps MiniLM, which was trained on natural
prose. The encoder was therefore run a second time on lightly cleaned text
keeping natural case and punctuation:

| Protocol | Shared normalised | Lightly cleaned | Difference |
|---|---|---|---|
| Stratified | 0.9167 | 0.9211 | +0.0044 |
| Merchant held out | 0.6479 | 0.6314 | -0.0164 |
| Strictly novel | 0.5936 | 0.5776 | -0.0159 |

Lighter cleaning does **not** help — it is marginally better on the easy protocol
and slightly *worse* on both harder ones. The single shared representation across
all five models is therefore defensible, and MiniLM's standing is not an artefact
of preprocessing.

## Unit 2 results, all five models

Macro-F1, validation sets. Test sets remain untouched.

| Model | Stratified | Merchant held out | Strictly novel | Merchant ECE |
|---|---|---|---|---|
| 1. Rule baseline *(17% coverage)* | 0.2924 | 0.2849 | 0.3068 | n/a |
| 1b. Merchant memory *(82% / 4% coverage)* | 0.8500 | 0.0752 | 0.0156 | n/a |
| 2. TF-IDF + Naive Bayes | 0.9809 | 0.5903 | 0.4657 | n/a |
| 3. TF-IDF + Logistic regression | 0.9976 | 0.5980 | 0.4636 | **0.0406** |
| 4. TF-IDF + Linear SVM | **0.9984** | 0.6393 | 0.5146 | 0.1452 |
| 5. MiniLM + Logistic regression | 0.9167 | **0.6479** | **0.5936** | **0.0360** |

No model wins outright. The SVM is most accurate on familiar merchants but its
confidence collapses under shift (ECE 0.1452). MiniLM is most accurate on
unfamiliar merchants *and* the best calibrated (0.0360), but weakest on familiar
ones and cannot explain itself token by token. Logistic regression is mid-table
on accuracy while being well calibrated and exactly interpretable.

Selecting a model to deploy therefore requires deciding what the application
actually needs, which is the subject of the next step.
